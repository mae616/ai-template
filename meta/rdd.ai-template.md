# 🎯 プロジェクト概要

## なぜ作るか（存在設計）
- 個人で作る意味は「速さ」ではなく**意図・存在設計が宿ったアプリを作ること**
- AI時代のWeb表現を探求したい
  - 作ったものにAIが当たり前に存在する
  - AIで実現できる新しい表現の探求
  - 「AIとの開発で自分の何が・人の何が拡張されたか」を問い続ける

## このテンプレートが解決する問題
- AIの汎用知識は豊富だが「自分の判断軸・こだわり・固有の手順・思想」は持っていない
- テンプレートなしだと毎回ゼロから伝え直す必要がある
- → skills / rules に書くことで「自分の分身」として機能させる

## 一言まとめ
> **意図・存在設計・体験設計が宿ったアプリを作るための、人間とAIの協調開発基盤**

# 🏗️ 設計思想（2層構造）

## 仕組み層（機械的に強制する）
- 担い手: hooks / CI/CD / TypeScript strict / ESLint / テスト
- 目的: 人も AI も関係なく**必ず実行される**品質ゲートを作る
- 「AIに指示する」ではなく「開発の仕組みとして設計する」

## 能力拡張層（自分の判断軸をAIに持たせる）
- 担い手: skills / rules
- 目的: 自分のこだわり・固有手順・思想をAIに持たせて**自分の能力を拡張する**

## AIの使い方の3軸
| 軸 | 内容 |
|---|---|
| コンテキストエンジニアリング | 意図・こだわり・スキルを明文化してAIに伝える。「揮発させないためにファイルに固める」 |
| ハーネスエンジニアリング | 品質・成果・作業量を仕組みで安定させる。AIができることを広げる |
| Vibe Coding | 人間の言語化できない感覚・判断でフィードバックを送る。「見て・感じて・修正する」ループ |

# 🧑‍💻 開発スタイル・インタラクション設計

## 基本スタンス
- 音声入力を使うため誤字・言い換えが混ざることがある
- **自律より「聞いて意図を反映」**が基本
  - 疑問の先出し・確認はOK
  - 確認なしの自律着手はNG
- **思考の見える化（モデル非依存）**: 作業の前に「何を考え、なぜそうするか」を言葉にしてから動く。判断基準はAIに委ねず人間が握る（どのモデルに変わっても維持する）
- スコープ・優先度の判断（今日何をやる/やらないか）は**毎回人間が決める**

## 自律度の使い分け

| モード | 内容 | 使う場面 |
|---|---|---|
| Human in the Loop | 人間が各ステップで判断・承認 | 設計・意思決定・スコープ確認 |
| Human on the Loop | AIが自律実行、人間が監督・要所で介入 | 実装ループ・レビューループ |

- 工程によって使い分ける。デフォルトは **Human in the Loop**
- Vibe Codingは「見て・感じて・言語化できない判断でフィードバックを送る」形で組み込む

## 確認フロー（目指す形）
1. **事前確認**: フローチャート＋**概念図（俯瞰レベル）**を提示してからGOをもらう
   - 俯瞰図（全体構造・概念）→ 詳細図（実装フロー）の順で出す
   - どちらを見るかは工程によって使い分ける
2. **作業実行**: AIが実行（Human on the Loop）
3. **事後確認**: AIレビューのループ → 人間の最終確認（Vibe Codingで感覚チェック）

## モデル運用方針
- 全工程のデフォルト: **Sonnet**
- Opusは現状2つの問題あり → **現時点では基本Sonnet**
  - ジリジリ自律着手してしまう（Human in the Loopに反する）
  - 対話が遅い
  - 上記が改善されればOpus使用を再検討する
- コンテキストが長くなったら: `/compact` してから続行

# 🏗️ 機能・構成

## 現状スナップショット（2026-06-11時点）
- スキル: 45個（`.claude/skills/`）
- フック: 4個（check-release-notes / post-edit-notify / validate-mermaid / warn-destructive-bash）
- ルール: 4個（code-quality / dev-practices / git / tool-usage）
- スクリプト: apply_template.sh / apply_global.sh
- 送り状雛形: `doc/output/to-template.md`（配布対象）

## フィードバックループ（送り状モデル）
- 各プロジェクトは汎用学びを自リポの送り状 `doc/output/to-template.md` に記録するだけ（ai-template を直接編集しない＝競合回避）
- 取り込みは ai-template 側で `/template-feedback` により直列処理し、反映済み項目は送り状の状態を `取込済` に倒す（二重取り込み防止台帳）
- テンプレに書くのは**判断軸・優先順位・困ったとき何を疑うか・固有の手順/思想のみ**（AIが既に持つ一般知識・固有例は書かない）

## ファイル・ディレクトリ命名方針
- 名前を見ただけで**役割・機能がわかる**ことを最優先
- プロジェクトのフォルダ構成を見ればアプリの機能が概ねわかる状態が理想
- `rdd.ai-template.md` はこの方針の体現（「何のRDDか」が名前でわかる）

## スキル構成とai-knowledgeとの関係
- **ai-template**（本リポジトリ）: 開発プロセス・判断軸・ワークフローの基盤
- **ai-knowledge**（兄弟リポジトリ）: 言語・フレームワーク・アーキテクチャ固有の知識
  - 言語ごとの思想・ベストプラクティス
  - アーキテクチャ思想（全体通しで1ファイルにまとめる方向で検討中）
  - React / Svelte / Tailwind / GSAP / Three.js 等
- 使い方: プロジェクト開始時にai-knowledgeから必要な技術スキルを追加する

## 読み手別ドキュメント方針
| 読み手 | 形式 | 理由 |
|--------|------|------|
| AI向け | Markdown | 軽量・シンプル・十分 |
| 人間向け | Markdown（概念図はMermaid等で補完） | XMLは人間が読めなくなるため採用しない |

> XMLはAI向けフォーマットとして有効だが、人間も読むファイルには使わない方針。

# 🛡️ 品質ゲート設計

## 優先順位
```
TypeScript strict → ESLint → テスト → CI → Dependabot
→ GitHub Code Scanning / Snyk → 危険変更チェックリスト
→ (任意) AIレビュー
```

## 危険変更チェックリスト（手動確認が必要な変更）
- [ ] 認証・認可
- [ ] 決済
- [ ] 個人情報
- [ ] DBマイグレーション
- [ ] 権限設定
- [ ] 外部API連携
- [ ] 削除処理
- [ ] 通知・メール送信

## AIレビューの位置づけ・フロー
- 「品質保証ツール」ではなく**「追加のレビューコメント生成ツール」**
- 品質ゲートを仕組みで固めてから、その外側に置く
- CodeRabbit: 現時点では保留。品質ゲートが整ってから再評価

### AIレビューのループ（必須）
```
/basic-review（表面チェック）
  → 致命的指摘が0になるまでループ
  → /deep-review（深いチェック）
  → 全指摘が0になるまでループ
  → 人間の最終確認（Vibe Codingで感覚チェック）
```
- `basic-review`: typo・命名・フォーマット等の表面チェック
- `deep-review`: 設計・セキュリティ・パフォーマンス等の深いチェック
- 致命的（critical）指摘が0になるまでは必ずループする
