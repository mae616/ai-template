03ガードは1件も止めていなかった

取り込んだ修正を当てる前後で、同じ10ケースを実測した。修正前は危険な操作6件すべてが exit 0 で通過していた。

BEFORE 4 / 10 危険ケース6件すべて素通り
AFTER 10 / 10 通す4件・止める6件が期待どおり
ケース期待修正前修正後
ls -la（git 以外）通す通過通過
git -C <task> commit通す通過通過
cd <task> && git commit通す通過通過
git -C <task> push origin HEAD通す通過通過
git -C <main> commit止める素通りブロック
cd <main> && git commit止める素通りブロック
git -C <main> push止める素通りブロック
git push origin HEAD:main止める素通りブロック
ブランチ判定不能止める素通りブロック
コミット0件リポジトリの main止める素通りブロック

原因は独立して3つあった

  • A. 人間の手癖を前提にした正規表現 — \bgit (commit|push)\b は git -C <path> commit に一致しない。人間は cd してから打つが、AI は作業ディレクトリを動かさずに済む -C 形を好む。入口で exit 0 するため、以降の判定に一切到達していなかった。同じ書き方が push 側にもう1箇所あった。
  • B. コミット0件のリポジトリ — rev-parse --abbrev-ref HEAD は文字列 HEAD を返す。main と一致しないので、初回コミットの瞬間だけガードが無効になる。最も起こりがちな場面に穴が開いていた。
  • C. cwd が当てにならない — フックは実行「前」に走る。cd <path> && はまだ効いておらず、-C は別リポジトリを指す。コマンド文字列からパスを抽出して判定する必要があった。

あわせて fail-closed 化。 判定できないときに通す実装は「守られている」誤認を生む。ガードが無い状態より悪い。判定不能は止める側に倒した。

04投函箱そのものが配布物を汚していた

取り込みのために作った投函箱を、apply_template.sh が除外していなかった。実際に一時ディレクトリへ配って確認したところ、そのままコピーされていた。

  • 他プロジェクトの受信データが全プロジェクトへ複製される（取り込むたびに増える）
  • /Users/<user>/... のローカル絶対パスが5箇所
  • private リポジトリの URL が1行

絶対パスは欠陥ではなく投函箱の価値の源なので、相対表記に直すと利点が消える。そこでパスを直すのではなく、受信データ自体をPCローカルへ閉じた。
