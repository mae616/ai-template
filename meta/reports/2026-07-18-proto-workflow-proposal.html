2026-07-18 ・ ai-template ワークフロー提案 ・ 承認済み・実装反映済み（auto-mvp → proto-loop 改修 / proto-medium 新設 / design-language 参照欄追加 / dev-practices 更新）

現行の /auto-mvp は「プロンプト1文 → 無指示で2〜4案並べる」発散だった。 これを、1案ごとに問いを立て、触った学びを「設定集」に蒸留し、次のプロトに継いでいく連作ループに変える。 AI動画制作の「キャラ設定資料を作り、それを見ながらプロンプトを磨く」やり方をソフトウェアの体験設計に持ち込む提案。 あわせて「これはFigmaでやるべきか、コードで作るべきか」の判断ガイドを新設する。

01何が変わるか — 現行と提案の比較

現行（auto-mvp）提案（proto-loop）
発散のしかた無指示で2〜4案を一斉に並べるラウンド制。毎回「このプロトで確かめたい問い」を人間と決めてから作る
学びの継承選定時に一度だけ言語化毎ラウンド設定集に蒸留し、次のプロトはそれを読んで始める
作り手同一文脈で連続生成1プロト＝1エージェント。設定集と課題だけを渡す（文脈遮断で新鮮な解釈を得る）
媒体常にコードFigma / コードを判断ガイドで使い分け（1ラウンド内の併用も可）
収束選定 → auto-build統合プロト（いいとこ取り1本）→ rdd反映 → auto-build。本番終盤に磨きラウンドを明示的に持つ

02全体フロー

03設定集（Setting Book）— この提案の中核

AI動画制作の「キャラクター設定表」に相当する、プロジェクトの世界観・体験の資料集。 プロトを作るたびに更新し、HTML化してアーティファクト公開する（開発者が見て「これいいね」と言える形）。

  • 置き場: doc/input/design/setting-book/（ソースはMarkdown、公開用にHTML生成）
  • 中身: 世界観・トーンの言語化 ／ 採用した表現（スクリーンショット＋なぜ良いか）／ 不採用の表現（なぜ違うか）／ 画面・レイアウトの型 ／ プロンプト集（次のプロトを作るための指示文そのもの）
  • SSOTとの関係: 設定集は「ビジュアル付きの発酵場所」。確定した判断だけを project-design-language スキル（SSOT）へ昇格する — judgment-harness の「メモとSSOTを分ける」原則そのまま

04Figma か、コードか — 判断ガイド（新設）

基準は一言でいうと 「止まっている絵で判断できるなら Figma、動かさないと分からないならコード」。

Figma が向く（Claude が MCP で操作）コードプロトが向く
・色・タイポ・レイアウトの比較検討（複数案を並べる）
・画面一覧・遷移フローの俯瞰
・デザイントークン・コンポーネントの整備
・人に見せて合意を取る資料
・手でドラッグして微調整したいもの 		・hover・スクロール・アニメーション等の触感
・実データ・レイテンシ・データ量が効く体験
・技術的に成立するかの検証
・レスポンシブの実挙動
・生成的・ゲーム的な「動きに世界観が宿る」表現
Figma側の実働はすでに揃っている: 書き込みは figma-generate-design / figma-use、実装への引き渡しは /design-ssot（Dev Mode からトークン抽出）。このガイドはそれらの「入口の交通整理」を担う。

05design-brain と Fable のデザイン思想の活かし方

ai-template は OSS なので、個人の審美眼（design-brain）を本体に埋め込まない。 代わりに「参照欄」だけをテンプレートに置く方式を提案する — 置き場所方針（配布物 vs 個人環境）と同じ考え方。

  • project-design-language 雛形に「外部デザイン知識ベース」欄（任意・パス記入式）を追加
  • 記入されていれば、設定集の生成・各プロト制作時に personal-style → anti-patterns → principles → patterns の優先順で読む（design-brain 自身が定める使い方そのまま）
  • プロトで得た「効いた/効かなかった」は design-brain の feedback/ へ還流（送り状方式）
  • Fableとのデザイン思想づくりは design-brain 側の personal-style/ を育てる活動として位置づける（テンプレとは切り離す）
