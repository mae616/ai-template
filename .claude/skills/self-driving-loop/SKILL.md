# self-driving-loop — 自己駆動ループ（実行の方法論）

モデルの「素の賢さ（重み）」は固定で上げられない。だが**手続き**は外から固定できる。
このスキルは「全体と今を両立しながら、自分の位置を見失わず、自分で仕様を立てて自分で検証しきる」振る舞いを、
**特定モデルの重みに張り付けず、手順として再現する**ための駆動ハーネス。

中核の考え方は1つ:

> **モデルを「生成器」としてだけでなく「検証器」として何度も回す。**
> 生成が弱くても、構造化された検証を反復すれば結果は収束する。

`judgment-harness` が「**何を良しとするか**（判断軸）」を育てる方法論なのに対し、
ここは「**どう駆動するか**（実行手順）」を固定する方法論。
**この手順はドメイン非依存。成果物の中身（具体的な仕様）は書かない。毎回その場で生成する。**
コード・文章・設計・データ・図・UI・3D など、対象が何であっても同じループを回す。

## 発火条件

- モデルが**一発目の出力で破綻しても自分で気づかず進む**領域を扱うとき
- 指示が**音声入力ぎみ・曖昧・大きい**ため、言われたことだけ満たして**意図を外す**事故を防ぎたいとき
- 長い作業で**全体ゴールを見失わずに**進めたいとき
- 「どのモデルで動いても**同じ良い動き**を引き出したい」とき（モデル非依存化）

> 既存ハーネスとの関係: `CLAUDE.md`「思考を見える化（モデル非依存・必守）」と `dev-practices.md`「考えていることを話しながら進める」を、**実タスクで実際に駆動する具体手順**に落としたもの。理念はそちら、手順はここ。

## 駆動ループ（5フェーズ）

各フェーズの冒頭で**何を・なぜ・どう判断したか**を1〜3行で宣言してから動く（沈黙実行しない）。
※具体例は理解の補助。**対象に合わせて Claude が効きやすい形に翻訳してよい**（特定ドメインに縛られない）。

### フェーズ -1: 入力の構造化
着手前に、受け取った指示を分解して**明示**する。ここを飛ばすと「指示は満たすが意図を外す」が起きる。

- **明示的な要求**: 言われたこと（言葉そのまま）
- **暗黙の意図**: 本当に達成したいこと／なぜ頼んだか
- **全体像のどこか**: このタスクは大きな目標の「どの一手」か
- **制約・前提・未定事項**: 曖昧な点は**推測せず明記**。意図が不明なときだけ短問で確認
- **完了の定義（DoD）**: 何が揃えば「終わり」か

### フェーズ 0: メタ認知の固定
全体と今をつなぐ**3文**を書き、以降のフェーズ冒頭で毎回参照する（長い作業で迷子にならないための錨）。

1. **全体ゴール（なぜ）**: このセッション全体で達成したいこと（1文）
2. **今の指示の意図（何を）**: この一手で求められていること（1文）
3. **接続（どうつながる）**: 今やることが 1 のどこに当たり、矛盾しないか（1文）

### フェーズ 1: 検証可能な仕様を自分で起こす
「良い出力とは何か」を、後で**確かめられる形**に翻訳する。**この中身は毎回生成する**（スキルに固定しない）。

- **構造に分解する**: 対象を構成要素・関係・制約に分けて箇条書き化する
  - 翻訳例: コードなら「入出力・境界条件・例外時の振る舞い・既存呼び出し元との整合」、文章なら「主張と根拠の対応・論理の順序・読者前提」、空間/UIなら「比率・対称性・要素間の位置関係」
- **「ありがちな破綻」を最低3つ自分で予測して列挙する**
  - ※破綻を先に言語化しておくと、フェーズ3の自己点検で必ず引っかかる。これが一番効く
  - 翻訳例: 「境界値でこける」「主張に根拠が付いていない」「左右非対称になる」など、対象固有の典型失敗
- **判定できる合格条件に変換する**: できるだけ**機械的・客観的に判定できる形**へ。難しければ「誰が見ても○×を付けられる observable な条件」に落とす

### フェーズ 2: 生成
フェーズ1の仕様に沿って作る。仕様にない判断が必要になったら、勝手に決めずフェーズ1へ戻して仕様に足す。

### フェーズ 3: 自己検証（収束するまで反復）
**順番が大事。曖昧な主観判定の前に、確実に判定できる検証を先に通す。**

1. **確実な検証を先に**: 機械的・客観的に判定できるものから確かめる（主観の「だいたい合ってる」を後回しにする）
   - 翻訳例: コードならテスト/型/実行結果、構造物なら寸法・対称・整合の計算、文章なら事実・引用・参照リンクの実在チェック
2. **複数の観点で確かめる**: 単一視点の自己評価は当てにならない。角度を変えて見る
   - 翻訳例: 正常系/異常系/境界、複数のアングルや画面幅、書き手視点/批判的読者視点
3. **基準との差分（あれば）**: リファレンス（既存パターン・正解例・本物の参照物・仕様書）を**目の前に置いて並べ、差分を述べる**（記憶からの再現より、比較対象がある方が正確）
4. **照合**: フェーズ1の仕様＆破綻リストと突き合わせ、**逸脱を箇条書き**にする
5. **収束**: 逸脱ゼロになるまでフェーズ2〜3を**最低2周**。各周の冒頭でフェーズ0の3文を再確認し、全体から逸れていないか見る

> **検証を省いて「できました」と報告してはならない。** 検証ログ（何を・どの観点で確かめ、残差は何か）を必ず残す。

## モデル非依存のキモ（なぜ効くか）

| 補う弱点 | 効く手続き |
|---|---|
| 言われたことだけ満たして意図を外す | フェーズ -1（入力の構造化） |
| 長い作業で全体を見失う | フェーズ 0（メタ認知3文を毎周参照） |
| 一発目の出力精度が低い | フェーズ 1（仕様＋破綻リストの事前言語化） |
| 破綻の見逃し | フェーズ 3-2/3-4（複数観点＋仕様照合の反復） |
| 主観判定の曖昧さ | フェーズ 3-1（確実な検証を主観より先に） |
| 記憶頼みの不正確さ | フェーズ 3-3（基準との差分） |

賢さを重みに頼ると属モデル的になる。手順をここに書けば、重みが弱くても手順が補う。**手続きの外部化＝モデル非依存化そのもの。**

## 強化オプション: 多エージェント敵対的検証

自己採点は甘くなる。堅さが要るとき（重要な成果物・重い検証）だけ、役割を**別エージェントに分離**する。
**トークンを多く使うため、ユーザーが明示的にそうしたいときだけ**発動する（自律ループの範囲は人間が指定する原則に従う）。

- **設計役**: 検証可能な仕様と破綻リストを起こす（フェーズ1）
- **生成役**: 作る（フェーズ2）
- **検証役（敵対的）**: 「これは仕様を満たしていない」と**反証しにかかる**。観点を分ける（複数の lens で別々に refute）
- **メタ認知監視役**: 各ステップが全体ゴール（フェーズ0）から逸れていないか監視

多数決で「過半が反証 → 棄却」のように収束させる。実装は `Workflow`（多エージェント）が適任だが、起動はユーザー合意の上で。

## やってはいけない

- フェーズ -1/0 を飛ばして即フェーズ2（生成）に入る（迷子・意図外しの主因）
- 確実な検証より先に主観で「だいたい合ってる」と判断する
- 検証を1周で打ち切る／検証を省いて完了報告する
- **このスキルにドメインの仕様（具体的な比率や個別ルール）を書き込む**（中身は毎回生成する。ここは手順だけ）
- 多エージェント検証をユーザー合意なく重く回す
