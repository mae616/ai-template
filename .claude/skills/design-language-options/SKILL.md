# design-language-options — 問いから選択肢を作り、並べて選ぶ

## このスキルが解く問題

着手時点では、人間もデザインの答えを持っていないことが多い。そこで「どんなデザインにしますか」と問い詰めると、答えられないか、ありがちな答えに寄る。
このスキルは逆に、**確かめたい問いから AI が選択肢を作り、事例とプロトで並べて、人間が「どれが近いか」で選ぶ**。選んだ学びは設定集に蒸留して、次のラウンドの材料にする。

> 下敷きは AI 動画制作の作法: 先に設定資料を作り、出力を見て資料を磨き、そこから本番を作る。ここでは「設定資料＝設定集」「出力＝事例とプロト」「本番＝auto-build」に当たる。

**範囲は、選択肢の提示と合意した学びの昇格候補まで。** 値の確定（F2）・画面を描く（F3）・本実装（auto-build）はしない。

## 入力: $ARGUMENTS
- 作りたいものの種（1文）、または既存の設定集のパス（続きから回す場合）

## レイヤー上の位置

| 何を | どこ |
|---|---|
| **問いから選択肢を作り、並べて選ぶ・学びを蒸留する** | **ここ** |
| Figma か、コードか（媒体の判断） | `references/medium.md` |
| 選択肢の1案ごとの導出（コンセプト一語 → 材質・配色・タイポ・シグネチャ） | `art-direction` |
| 選んだものを値・ドック・画面一覧に書く（F2） | `design-consistency` / `design-doc` |
| プロジェクト固有の方針と索引 | `project-design-language` |

## 3つの軸

1ラウンドで扱う軸を、問いから選ぶ（全部を毎回やらない）。

| 軸 | 何の選択肢か | 例 |
|---|---|---|
| デザイン言語 | 材質・配色・タイポ・余白の密度・形 | 紙のように静か／ガラスのように軽い |
| モーション言語 | 何がどう動くか・速さ・止まり方 | 置かれるように止まる／弾んで止まる |
| 声 | 呼びかけ方・語彙・文の長さ（一般則は `design-fundamentals` の `references/ux-writing.md`） | 道具として短く／隣で話すように |

## 成果物の置き場

| 成果物 | 置き場 | 性質 |
|---|---|---|
| 設定集（Setting Book） | `doc/draft/design/setting-book/`（ソースの MD。`index.html` にまとめて人間に見せる） | **未合意**の下書き。判断盤の結果・採用と不採用の理由・事例・プロンプト集 |
| 判断盤 | 設定集の `index.html`、またはラウンドごとの HTML | 人間が選ぶ場所 |
| 事例の画像 | `doc/draft/design/setting-book/refs/`（作るときに、中身が `*` だけの `.gitignore` を置く。`index.html` からは相対パスで参照し、HTML に埋め込まない） | 判断盤に貼るための手元の写し。**コミットしない**（第三者の画像。利用規約を確かめていないので再配布しない）。設定集には引用元のリンクを書く |
| プロトタイプ | `proto/*` ブランチ または `samples/proto-N/`（本番ビルド・配布から除外） | 使い捨て |
| Figma の案 | Figma ファイル（URL を設定集に書く） | 使い捨て〜値の種 |
| 確定した判断 | デザインドック（`doc/input/design/docs/`）と値のファイル（`doc/input/design/design-tokens.json` 等） | **人間の合意後のみ**（F2 で書く） |

## 実行手順

### 0. 設定集を用意する（初回のみ）
- `project-design-language` を読む。`TBD`（決めていない）のままの項目は、推測で埋めずに `TBD` のまま進む
- 外部のデザイン知識ベースの欄が埋まっていれば、その優先順で読み、以後のラウンドの前提にする
- 設定集の骨組みを作る: 世界観・トーン／採用した表現／不採用の表現／画面の型／プロンプト集
- 設定集の索引に、ラウンドごとの1行（問い・選んだ案・**結論の行き先**）の表を置く。**結論の行き先が空欄の行＝昇格し損ね**（`design-doc`「索引に結論の行き先を持つ」）

### 1. 問いを立てる（人間と・毎ラウンド必須）
- 「このラウンドで何を確かめたいか」を人間と1〜3行で決める。例:「初回の第一印象は静かな方がいいか、賑やかな方がいいか」「この操作は直接操作か、コマンドか」
- 人間が答えを持っていなくてよい。**問いだけ決めて、答えの候補は AI が出す**
- **問いなしで選択肢を作り始めない**

### 2. 事例を集める
- **Mobbin MCP が使えるとき**（`/setup` が rdd の「運用環境」に書いた答えを見る）。次の4つは Mobbin MCP のツール説明（`search_screens`、2026-10-02 確認）の指示。使う前に、その回のツール説明と食い違っていないかを見る:
  - 検索語は**1画面を具体的に**書く（UI の要素とその関係。例: 「プロモコード欄と Apple Pay ボタンがある決済画面」）。複数の画面・否定・「モダン」のような曖昧な形容は入れない
  - 人間に見せる事例には、**必ず `mobbin_url` をリンクで引用する**
  - 画像を保存・判断盤に貼るときは、**`image_url` からダウンロードする**（URL は30日で失効する。リンクを貼るだけにしない）
  - 結果に `ai_usage_notice` があれば、**一字一句そのまま**、結果のあとに独立した塊で見せる（要約・言い換え・他の文との合成をしない）
- **使えないとき**: Design Inspiration 系のサイトから集める。どのサイトから取ったかを、画像ごとにリンクで残す
- 事例は「この問いの答えの候補」として集める。似たものを並べるのではなく、**問いの軸の両端と中間**が見えるように選ぶ

### 3. 選択肢を作る
- 1ラウンド2〜3案。**案と案の違い（比較軸）を1行で言えるもの**だけを並べる。軸のない3案並列はしない
- 各案を `art-direction` の導出線（コンセプト一語 → 材質・配色・タイポ・シグネチャ）で書く。事例はその根拠として添える
- 媒体（止まった絵か、動くプロトか）は `references/medium.md` で決め、**推奨と理由を一言**添えて人間に確認する
- プロトを作るときは、**1案＝1つの新しいサブエージェント**に、設定集＋今回の問い＋（あれば）外部知識ベースの参照**だけ**を渡して作らせる（会話履歴は渡さない。文脈遮断で新鮮な解釈を得る）。サブエージェントが無い環境では、新しいセッションで同じ材料だけを渡す
- プロトの品質ゲートは最小限（動く＋スクリーンショット）。テスト・レビュー収束・PR は作らない

### 4. 選択肢を批評する（作る → 批評する）
人間に見せる前に、次の2段で当てる。

**1案ずつ（文脈遮断）**: 案ごとに `design-critic` を起こし、**その案のスクリーンショット（Figma の案は書き出した画像）＋その案の AD宣言（`art-direction` の出力）だけ**を渡す。design-critique のルーブリック全問で見るが、F1 で特に効くのは次の2問。サブエージェントが無い環境では、新しいセッションで同じものだけを渡す。

| 問い | NO のとき |
|---|---|
| **匿名テスト**（Q1）: プロダクト名を隠したとき、他のアプリと区別がつくか | 汎用に寄っている。導出線からやり直す |
| **導出線**（Q2）: 目につく判断（材質・色・語）を、コンセプト一語から説明できるか | 根拠の無い判断を外すか、コンセプトを言い直す |

**案どうし（このスキルの実行者が当てる）**: 複数案と問いが揃わないと答えられないので、批評者には渡さない。

| 問い | NO のとき |
|---|---|
| **比較軸**: 案どうしの違いが、問いの軸の上で読めるか | 違いが軸の外にある。案を作り直す |

動き（モーション言語）はスクリーンショットでは批評できない。媒体がコードの案は、ステップ5で人間が触って確かめる。

### 5. 判断盤で人間が選ぶ（必須）
- 案ごとに、事例の画像・プロトのスクリーンショット（または Figma の URL）・比較軸・推しと根拠を並べる
- **媒体がコードの案は、人間が実物を触ってから選ぶ**。判断盤にはプロトの起動方法か URL を置く（動き・触感は静止画では選べない。`references/medium.md`）
- 人間は「どれが近いか」「どこが違うか」で選ぶ。言語化しにくければ二択で拾う
- 判断盤の作り方と出し方は `report-publish` に従う（Artifact なら非公開のまま見せる。使えなければローカルの HTML を開き、選んだ結果をコピーして貼ってもらう）
- ここは Human in the Loop。**飛ばして次のラウンドへ進まない・1案へ収束させない**

### 6. 設定集へ蒸留する
- **採用した表現**: プロトのスクリーンショット（git に入れてよい）＋なぜ良いか。事例（第三者）の画像は git に入らないので、**画像が無くても伝わる言葉**（何が・なぜ良かったか）と引用元のリンクで書く
- **不採用の表現**: なぜ違うか（負の例は、ありがちへの回帰を止める一番強い制約）
- **プロンプト集**: 次のラウンドを作る指示文を、今回の学びで書き直す
- 索引の表にこのラウンドの1行を足す（結論の行き先は、決まるまで空欄）
- 設定集の `index.html` を作り直し、ステップ5と同じ扱いで人間に見せる（Artifact なら非公開のまま、同じ URL を保つ。共有するかは人間が決める。共有する版には事例の画像を入れず、引用元のリンクだけにする）
- **昇格候補に印を付けて人間に見せる**。上げるかどうかは AI が決めない（`judgment-harness`: 発酵場所のメモと確定した SSOT を分ける）
- 人間と次を決める: **もう1ラウンド回すか、収束に向かうか**／**昇格候補を上げるか**

### 7. 統合プロト（収束するとき）
- 各ラウンドの「採用」を束ねた1本を、新しいサブエージェント＋設定集で作る
- 人間が触って確認する。出た「もう少し」は設定集に書いて統合プロトに反映する

### 8. 次の工程へ渡す
- **昇格（人間の合意後のみ）**: 上げると決まった判断は、F2（`design-consistency` / `design-doc`）で値・デザインドック・画面一覧に書く。書く文面か差分を見せて合意を取る（`.claude/rules/dev-practices.md`「一時と確定を分ける」）。判断盤で選ばれたものはまとめて書いてよい
- **要件へ上げるもの**: 設定集から「要件になりうるもの」を一覧で見せ、上げると決まったものだけ、`rdd.md` に書く文面を見せて合意を取ってから書く（プロトが完走したことと、要件になることは別）
- **昇格し損ねの確認**: 索引の表で「結論の行き先」が空欄の行を一覧にして人間に見せ、上げる・捨てる・持ち越すを決めてもらう
- 本実装は `auto-build --from-proto <設定集パス>`（プロトのコードは仕様の種。本実装は TDD で作り直す）

## やってはいけない
- 問いを立てずに選択肢を作り始める（無指示の並列発散を含む）
- 事例を引用元のリンク無しで見せる／Mobbin の `image_url` をリンクだけで残す／事例の画像をコミットする
- 人間の選択を経ずに次のラウンドへ進む・1案へ収束させる
- プロトでの TDD・レビュー収束・PR（後段の auto-build がやる）
- プロトのコードをそのまま本番に残す（`samples/` / `proto/*` の扱いを崩さない）
- 設定集を更新せずにラウンドを終える（学びが揮発する）
- ⚠️ ラウンドの途中で `doc/input/`（rdd.md・デザインドック・値のファイル）へ書く。書けるのは `doc/draft/` だけ
- ⚠️ 昇格の可否を AI が決める。候補の提示までが担当
