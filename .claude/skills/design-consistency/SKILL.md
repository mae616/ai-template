# design-consistency — 定義を作り、当て、古くさせない

## このスキルが答えること

新しいプロダクトを作るたびに、同じ3つで詰まる。

1. **何の定義を作ればいいのか**（決め忘れると、画面ごとにその場の勘で決まる）
2. **どうやって全画面に当てるのか**（1枚ずつ直すと終わらない）
3. **どうやって古くならないようにするのか**（定義が実物より遅れると、古い状態が現状として扱われる）

⚠️ このスキルは定義の**中身**を持たない。中身はプロジェクト側（`project-design-language`・値のファイル・デザインドック）が持つ。

> **書き込みの関所**: `doc/input/design/` への書き込みは、`.claude/rules/dev-practices.md`「一時と確定を分ける」に従う（文面か差分を見せて合意を取る。判断盤で選ばれたものはまとめて書いてよい。自律ループ中は `doc/draft/` に候補として置く）。

## 発火条件

- 新しいプロダクトのデザイン定義をゼロから立ち上げるとき
- 画面を**5枚以上**まとめて作る前
- 「画面ごとにバラバラ」「統一感が無い」「定義したはずなのに適用されていない」と言われたとき
- 既存の定義を全画面に一律で当てるとき

## レイヤー上の位置

| 何を | どこ |
|---|---|
| 配置・文字・色・操作・文言の一般則 | `design-fundamentals` |
| 描く瞬間の演出規律 | `art-direction` |
| 決めごとの書き方（主題ごとのドック） | `design-doc` |
| 決めごとと実物の照合（数える） | `design-audit` |
| 描いたあとの文脈遮断レビュー（見る） | `design-critique` |
| 置き場の原則（値・判断・履歴） | `.claude/rules/doc-writing.md` |
| **決めるものの一覧・当てる手順・保つ時点** | **ここ** |

## 第1部: 何の定義を作るか（チェックリスト）

⚠️ **最初に全部決めない。** 決められないものを埋めると、推測が確定物の顔をして残る。決めていないものは**「決めていない」と書く**（値のファイルの `undecided`、ドックの「まだ決めていない」）。
⚠️ **逆に「あとでまとめて」にもしない。** 描いてから決めると、決めた分だけ描き直しになる。

### レベル0 — 最初の1画面を描く前

- [ ] 質感ワード3語（あとの全部がここから導かれる）
- [ ] 単一メタファー（この製品は何に喩えられるか）
- [ ] 基調の色: 地／面／文字／副次／罫線
- [ ] 書体と、使う最大ウェイト（声量の上限）
- [ ] 主な利用者は誰か。衝突したとき誰を優先するか
- [ ] 声とトーンの位置（`design-fundamentals/references/ux-writing.md` の4軸）

### レベル1 — 5画面を描く前

- **色と意味**: 色を使ってよい場所／主ボタンの色は何種類で何を意味するか／警告色を使う唯一のケース／色だけで意味を伝えない担保
- **文字**: 文字サイズの段（段ごとに役割の名前）／文字色の数／画面幅ごとの対応表／小さい方の下限（実機で決める）
- **操作要素**: ボタン・リンク・平文の使い分け／ボタンの階層（3段を超えると重い）／アイコンの作法（線か塗りか・線幅・単独で置いてよいか・ラベルの前か後ろかの軸）／入力欄の型
- **余白**: 余白の刻み（使ってよい値の一覧）／左右余白／上余白（端末の切り欠きに隠れない値を実機で）

### レベル2 — 画面が10枚を超える前

- **画面の骨格**: ヘッダーの型／画面タイプの分類（入口・一覧・作業・確認・選ぶ・設定 など）と、タイプごとに骨格をどう変えるか（⚠️ 同じ骨格を全画面に流用しない）／1画面の情報量の上限
- **出口と戻り**（一番割れる）:
  - 戻るのラベルは系統を分ける: フローを進んで来た → そこで何をするか（動詞句）／階層を降りた → 「〜に戻る」／複数の経路から来る → 「戻る」（嘘の行き先を書かない）
  - やめる・閉じる・戻るの行き先は、判断基準を1本決める（例: 操作の結果、何が残ったかで決める）
  - 確認画面を挟む条件（例: 取り戻せないときだけ）
  - モーダルを使ってよい場面（唯一無二の表現は、流用した瞬間に特別さを失う）
  - 出口の下に置く補足1行の形（この形に乗らない一言は補足ではない）
- **画面遷移**: 遷移の向き（深く入る／一時的な作業／戻る）を種類ごとに1つに決める
- **言葉**: 同じ操作を指す言葉を1つに固定（1文字違いの語を隣り合わせない）／画面を指す言い方（「前の画面」等の指示語を使わない）／操作の名前に「したあとどうなるか」まで書くか／固有名詞・URL の表記（省略形を作らない）
- **保存と中断**: 自動保存するか、いつどこに状態を出すか／状態表示を**出さない場面**（まだ何も残していないのに「書きかけ」と出すと情報が濁る）／どこからでも降りられるか（降りる出口を押しにくくしない）

### アクセシビリティはレベル0から並走させる

最後に検品する工程にしない。後から当てると、表現と両立できなくなってから作り替えることになる。判断軸は `accessibility-engineer`。

| いつ | 見るもの |
|---|---|
| レベル0（基調色を決めた瞬間） | 文字色 × 地／面のコントラスト（地の上と面の上は別々に測る） |
| レベル1（文字の段・色の意味） | 小さい方の下限を実機で／色以外の手がかりを同時に決める |
| レベル2（操作要素の型） | タップ領域・キーボード操作・読み上げの順序 |
| 描いた直後 | 上の項目が守れているかの点検（`design-critique` Q15・`design-audit`） |

🔑 アクセシビリティと表現が衝突したら、表現側を作り替える。OS が持てる設定（文字サイズ・ダークモード・動きを減らす）は追従に倒し、重複のトグルを作らない。

## 第2部: 画面の採番規則（先に決める）

| 決めること | 例 |
|---|---|
| 接頭辞の意味 | `S`＝アプリ内画面／`W`＝Web の単独ページ |
| 番号の意味 | **追加順**（フローの順にしない。フローは変わるが、番号は変えられない） |
| 枝番の意味 | `S16b`＝`S16` から降りる1段下 |
| 状態を画面にするか | **しない**（同じ画面の別状態として扱う。デザインツールの枚数と画面数は一致しなくてよい） |
| 欠番 | 埋めない |

画面の一覧・採番・繋がりは `doc/input/design/screen-map.md` に書く。

## 第3部: どこに置くか

原則は `.claude/rules/doc-writing.md` §1（値・判断・履歴を混ぜない）。デザインでの置き場はこう分ける。

| 置き場 | 何を書くか | 書かないこと |
|---|---|---|
| 値のファイル（`doc/input/design/*.json`。スキーマは `ssot_schema.md`） | 値だけ。`meta.decision` と `undecided` を持つ | 理由・経緯 |
| デザインドック（`doc/input/design/docs/`） | 主題ごとの「決まっていること／なぜ／まだ決めていない」 | 値・時系列 |
| 画面の一覧（`doc/input/design/screen-map.md`） | 画面・採番・繋がり | 見た目の決め |
| `project-design-language` | 基本方針と、ドック・値への**索引（薄い案内板）** | 本体を抱え込む |
| 要件（`doc/input/rdd.md`） | 仕様 | デザインの試行錯誤 |
| 経緯 | コミットメッセージ（発酵中の検討は `doc/draft/`） | — |

### デザインツールの「状態」を、置き場で表す

確定していないものが確定物に流れ込む事故は必ず起きる。ページ（置き場）を状態で分ける。

例:

```
00 読み方 › 01 ✅ 確定 › 02 🔬 試行錯誤 › 03 📝 未検証 › 04 📐 没案
```

確定物（値のファイル・ドック・実装）へ反映してよいのは `01` だけ。⚠️ 反映そのものを止めない。**反映元を `01` に限定する**（`.claude/rules/dev-practices.md`「一時と確定を分ける」）。

## 第4部: どう当てるか（一律適用の手順）

> ⚠️ **1枚ずつ直さない。先に法則を決めてから、全画面に当てる。** 1枚ずつ直すと、直した枚数だけ新しい多数派ができて終わらない。

1. **実測する**: 同じ役割の要素が、いくつの値に割れているかを機械で数える（`design-audit`）。揃っている所は揃っている。実測は直す対象を減らすためにも効く
2. **法則を決める**: 基本は多数派に従う。実機での可読性が上回るときは外し、外した理由をドックに書く
3. **既存の確定事項と照合する（当てる前に）**: 衝突したら「どちらかを取る」の前に、両立する第三の案を疑う
4. **条件で走査して当てる**: 対象をリストで挙げない。人が数えると必ず漏れる
5. **3層で点検する**: 数値／並び（要素の有無と順序）／作り（同じ役割が同じ作り方か）。名前で走査しない。名前は「作り」の層で、2通りの作りが混ざっていないかを見るときにだけ使う（`design-fundamentals`「一律に当てるときの手順」）
6. **当てたあと、法則に合わなかった場所を拾う**: 法則を当てる作業は、法則の穴を炙り出す作業でもある
7. **決定が効かない場合を1つ挙げる**: 「行に印を出す」と決めたら「行が無いときは？」と聞く
8. **表示を足したら、既存と重なっていないか見る**
9. **文言を直したら、その場で動線（遷移）も直す**: 別の回に回すと、次に触ったとき嘘をつく

## 第5部: どう古くさせないか

原則は `.claude/rules/doc-writing.md` §3（宣言ではなく照合の時点を決める）と §7（止めた判断を残す）。デザインでの照合の時点はこう決める。

| いつ | 何を照合するか |
|---|---|
| 画面を作る直前 | 使う値が値のファイルと一致しているか |
| 値を変えたとき | その値を持っている場所を全部洗い出して直す |
| 画面が10枚増えたとき・決めごとを足した直後 | `design-audit` を回す（足した規則は既存の実物に必ず違反が出る） |
| セッション開始時 | 前回の決定が置き場に入っているか |

- 画面数・件数・「もう有る／まだ無い／古い」は実測してから書く（`dev-practices.md`「思い込みより実測」）
- 予定を書く表と、現状を書く表を混ぜない（`dev-practices.md`「一時と確定を分ける」）

## 第6部: 新しいプロダクトでの進め方

```
0. 置き場を作る（値のファイル・ドックの索引・screen-map を空で）
1. レベル0 を決める
2. 最初の1画面を描く（design-fundamentals / art-direction）→ design-critique → 人間が触る
3. レベル1 を決める
4. 5画面まで描く（違うタイプの画面を選ぶ）→ design-critique → 人間が触る
5. レベル2 と採番規則を決める
6. 残りを描く
7. 一律適用（第4部）→ design-audit で外れ0件
8. 実装へ（値は値のファイルから引く。絵から写さない）
```

## よくある落とし穴

- **定義が無いから適用されない、と考える。** 実際には定義はあるが**読める形をしていない**ことが多い。作る前にまず数える（何が有って、何が無いか）
- **新しい定義を足して解決しようとする。** 置き場が増えると、どれが正か分からなくなる
- **同じ失敗を繰り返す。** やらかしは記録するだけでなく、手順（チェックリスト）に変える
- **一貫性のために全画面へ同じ骨格を流用する**（→ 単調さ。`design-fundamentals` 反復）
