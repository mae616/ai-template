# design-audit — 決めごとを実物に照合して数える

## このスキルが答えること

**決めごとは、書いた時点では守られている。割れるのはそのあと。** そして、割れの多くは目で見ても気づけない。

- アイコンの大きさが数通りに割れている
- 線幅が、大きさに対する比で見ると一部だけ外れている
- 同じ役割の印が、文字の記号とアイコン部品の2通りで作られている
- 文字サイズの段が、決めた段と実物でほとんど噛み合っていない
- 主ボタンの文字のコントラストが基準に届いていない

🔑 どれも「見て気づく」ものではない。**数えたから出る。**

> **書き込みの関所**: `doc/input/design/` への書き込みは、`.claude/rules/dev-practices.md`「一時と確定を分ける」に従う（文面か差分を見せて合意を取る。判断盤で選ばれたものはまとめて書いてよい。自律ループ中は `doc/draft/` に候補として置く）。

## 発火条件

- 画面が増えたあと（10枚単位で増えたら）
- **決めごとを足した直後**（足した規則は、既存の実物に対して必ず違反が出る）
- 実装に渡す前（`auto-design` / `auto-build` の前）と、実装したあと（実装の画面に対して）
- 「揃っていない気がする」と感じたとき（感じただけで直さない。数える）

## design-critique との違い（重複させない）

| | 見るもの | やり方 |
|---|---|---|
| `design-critique` | 絵の違和感（ルーブリック） | **定性**。文脈を切った目で見る |
| **`design-audit`（ここ）** | 決めごとと実物の差 | **定量**。数えて分布を出す |
| `design-consistency` | 定義の作り方・当て方 | 作る側の工程 |

両方要る。批評は「チカチカする」を拾い、検品は「この段の文字が何件、段の外が何件」を拾う。

## 手順

### 1. 走査の範囲を先に決める（飛ばすと数字が嘘になる）

- 範囲を決めずに数えると、注記・比較用のフレームまで数えて件数が膨らむ
- **名前だけで絞らない**（未採番・命名待ちのものが落ちる）。**幅だけでも絞らない**（同じ幅の注記が紛れ込む）。型・実寸・親子関係を組み合わせる
- 条件から落ちたものを一覧で出し、目で見る
- **件数だけを書き戻さない。条件式ごと書く。** 件数だけだと、次に数えた人（AI 含む）は「増えたのか、範囲が違うのか」を判定できない。**一致したから正しい、ではない**（条件の外に画面が残っていることがある）
- 何を対象にしたかを必ず出力に書く

### 2. 照合の相手（正）を先に読む

値のファイル（`doc/input/design/*.json`）とデザインドック（`doc/input/design/docs/`）。記憶から書かない。

正の側が壊れていることがある（自己矛盾している、実物を語っていない）。そのときは**それも所見に書く**。実物だけを疑わない。

### 3. 数える（規則ごとに分布を出す）

「違反が何件」の前に「**何がいくつあるか**」を出す。分布を見ないと多数派が分からない。

⚠️ 多数派＝正解ではない。多数派は「どちらに寄せるのが安いか」を示すだけ。正解は値のファイルとドックにある。無ければ**未決**（→ 手順7）。

### 4. 見えないものを測る

枠の数字だけ見ても割れは出ない。**実際に描かれている範囲**を測る。

| 測るもの | 何を見るか |
|---|---|
| 線画の実寸 | 線の太さを含めた描画範囲（枠が同じでも中身の大きさが違う） |
| 実際の余白 | 線画の端から隣の要素の端まで（レイアウトの間隔の指定値は見た目ではない） |
| コントラスト | 文字の色と、**祖先をたどった**背景の色 |
| 押せる領域 | 当たり判定の箱の実寸（見た目の枠 ≠ 当たり判定） |
| 線幅の割れ | 線幅を絶対値でなく、大きさに対する**比**で数える |

デザインツール（Figma）での測り方は `references/figma-measure.md`。実装の画面では、ブラウザの計算済みスタイルと描画範囲で測る（測る前に動きを止める）。

### 5. 文言の割れを拾う（数えるだけでは判定できない層）

短い文言（ラベル・ボタン）を集め、同じ概念の言い回しを並べる。出てきた候補は**4つに仕分ける**（全部を「割れ」として直さない）:

| 種類 | 例 | どうするか |
|---|---|---|
| ① 同じ操作に2つの名前 | 「リンクをコピー」と「URLをコピー」 | **直す** |
| ② 文脈で説明はつくが、決めごとが無い | 「ホームに戻る」と「保存せずホームに戻る」 | 文言は触らず、**使い分けをドックに書く** |
| ③ 別の操作なのに語が近い | 「削除」（取り戻せない）と「非表示」（戻せる） | **軸を言葉にしてから**、外れている方だけ直す |
| ④ 名前と文言の食い違い | 部品名「次へ」／文言「送信する」 | **名前を文言に合わせる**（状態の表示は例外） |

- ②を①として直すと、文脈の違いを消してしまう。先に「なぜ違うのか」を人に確かめる
- ③が一番見つけにくい。どちらでも意味が通る語ほど割れる。軸（手元か／相手へか、など）を先に言葉にする
- ④を放置すると、以後の検品で名前を条件に使えなくなる

### 6. 出力する（表1枚。直したことを混ぜない）

```
対象: {条件式} ＝ {N画面 / Mテキスト}
| 規則 | 違反 | 割合 |
| 文字サイズが決めた段の外 | {件数} | {割合} |
| コントラスト 4.5 未満 | {件数} | {割合} |
内訳（悪い順）: …
```

- 件数と割合を必ず書く。「いくつか割れている」と書かない
- 内訳は多い順ではなく**悪い順**（コントラストなら比が低い順）
- 検品と修正は別の段。所見に「直しました」を混ぜない

### 7. 直す／直さないを分ける（ここが一番大事）

| 種類 | どうするか |
|---|---|
| 正に照らして明確に外れ | 直す |
| 正に無い | **勝手に決めない。** 値のファイルの `undecided` に書いて人間に返す |
| 正の側が実物と食い違う | どちらを正にするか**人間に聞く**（実物が正のことも多い） |
| 条件つきで承認済みの例外 | **条件が守られているかを別に数える**（承認の事実だけ読まれ、条件は読まれない） |

🔑 **「この規則の対象外」は「すべての規則の対象外」ではない。** ある規則で対象外にしたもの（例: 大きさを揃える規則で記号を対象外にした）を、**残りの規則（線幅など）で数え直す**。漏れは対象外の集合に溜まる。あわせて値のファイル側に**対象外の範囲**を書く（「対象外なのは◯◯の規則だけで、△△には従う」）。

### 8. 直したら再走査して 0 件を確認する

同じ走査をもう一度流し、外れ0件を数字で確認する。直す順番に依存があるもの（大きさを変えると余白が変わる、など）は、依存をドックに書く。

### 9. 参照の古さを当てる（値の検品では出ない層）

ドックやスキルが「デザインツールの◯◯にある」と指しているノードやページが、移動・削除されて実物とずれていないか。値は数えれば出るが、**参照の古さは数に出ない**。参照を全部抜き出し、実物を引いて突き合わせる（`references/figma-measure.md`）。

## やってはいけない

- 名前で走査する（レイヤー名は揺れる。型・実寸・親子・色で走査する）
- 範囲を決めずに数える
- 多数派を正解として自動で寄せる
- 正に無い値を、その場の理屈で決める（「揃っている方が綺麗だから」は根拠ではない）
- 機械的な分類で形を判定する（絵が何の形かは人が見て決める）
- デザインツールのコメントに所見を残して終わる（読みに行かれず流れる。所見はリポジトリに出す）
- 動きが走っている画面をそのまま測る（現れの途中の位置で、嘘の差が出る）

## 収束条件

1. 対象範囲を条件式で書いた
2. 規則ごとの件数と割合を出した
3. 直したものは再走査で0件を確認した
4. 直さなかったものは `undecided` かタスクボードのカードになっている（会話に置き去りにしない）

## 書き戻し先

| 何 | どこ |
|---|---|
| 値（サイズ・色・比率・文言） | `doc/input/design/*.json` |
| なぜそうなっているか | `doc/input/design/docs/`（主題ごと） |
| 未決 | 値のファイルの `undecided`（「無い」ではなく「決めていない」と書く） |
| やること | プロジェクトのタスクボード |
